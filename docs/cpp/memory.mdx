
# Memory

## Low-Level Basic Memory Management

### `malloc`

- Syntax: `void* malloc(std::size_t size)` 
- If allocation succeeds, returns a pointer to the lowest (first) byte in the allocated memory block that is suitably aligned for any scalar type 
- On  failure, returns a `nullptr`
- If `size` is zero, the behaviour is implementation defined (null pointer may be returned, or some non-null pointer that may not be used to access storage but has to be passed to `std::free`)
- How `malloc` works under the hood
    - `malloc` is actually just a user-space library function that manages a pool of memory
    - Internally it calls `sbrk` and `mmap` (wrappers around the actual system calls) to expand that pool
    - `brk` is the boundary marking the end of heap data segment, `sbrk` (set break) is used to increment or decrement it by a number of bytes 
    - Think of `malloc` as a retailer that buys memory "wholesale" from the kernel, and sells it to the programmer at exactly the right size that was requested 
    - Calling `delete` or `free` marks a region of memory as freed, which `malloc` can reuse first before requesting new virtual memory pages from the kernel
    - Small allocations (usually under 1 MB or 128 KB) stay inside the program's free-list pool indefinitely. Large allocations are often allocated using system commands like mmap and are returned to the OS immediately upon being freed
    - The heap behaves like a continuous LIFO stack. Heavy reliance on `sbrk` can lead to fragmented memory. `mmap` skips the traditional heap entirely - it tells the kernel to find an empty gap anywhere in your virtual address space and map a fresh block of memory pages there
    - Unlike `sbrk`, regions created via `mmap` can be completely unmapped (`munmap`) in any order at any time. When used by `malloc` for general RAM, it uses a flag called `MAP_ANONYMOUS`, meaning the memory isn't backed by any physical file on your storage disk

### `new`

- Allocates storage and attempts to construct and initialize either a single unnamed object, or an unnamed array of objects in the allocated storage
- Returns a prvalue pointer to the constructed object, or if an array of objects was constructed, a pointer to the initial element of the array
    - On failure, throws `std::bad_alloc`
    - Using `new (std::nothrow) ...`, it returns a `nullptr` on failure instead
- The memory allocator may allocate a slightly larger block of memory than requested
    - This extra space is reserved for metadata to manage the allocated memory
    - This metadata is commonly referred to as the _allocation header_, _heap header_, or _control block_
    - The pointer returned by `new` is offset to point to the usable memory after the header
    ```cpp
    int* arr = new int[10];
    arr++;
    delete[] arr; // UB
    ```
- Syntax: 
    - (1) `new (type) initializer` 
    - (2) `new type initializer` 
    - (3) `new (placement-args) (type) initializer`  
    - (4) `new (placement-args) type initializer`
    - Syntax (1) or (3) is required if `type` includes parentheses
    ```cpp
    new int(*[10])();    // error: parsed as (new int) (*[10])()
    new (int (*[10])()); // ok, allocate array of 10 pointers to functions
    ```
    - If `type` is an array type, all other dimensions other than the first must be specified as positive integral constant expressions
    - The first dimension _may_ be an expression of integral type, enumeration type, or class type with a single non-explicit conversion function to integral or enum type (before C++14) / any expression convertible to `std::size_t` (since C++14), **only when using un-parenthesized syntax** (2) and (4)
    ```cpp
    int n = 42;
    double a[n][5]; // error
    auto p1 = new doule[n][5];    // ok
    auto p2 = new double[5][n];   // error, only first dimension may be non-constant
    auto p3 = new (double[n][5]); // error, syntax (1) cannot be used for dynamic arrays
    ```
    - The behaviour is undefined if the first dimension is negative
- Type is parsed greedily; it will take every token that can be part of a declarator
```cpp
new int + 1; // ok
new int * 1; // error, parsed as (new int*) (1)
```
- `new` can be used with `auto` and class template deduction (there are some extra rules where the initializer is not optional)
- The objects created by `new` expressions (objects with dynamic storage duration) persist until the pointer returned by the expression is used in a matching _delete-expression_
    - If the original value of the pointer is lost, the object becomes unreachable and cannot be deallocated, leading to a _memory leak_
    ```cpp
    int* p = new int(7);
    p = nullptr; // memory leak

    void f() {
        int* p = new int(7);
        // memory leak
    }

    void f() {
        int* p = new int(7);
        g(); // may throw 
        delete p; // okay if no exception
    } // memory leak is g() throws
    ```
    - To simplify management of dynamically allocated objects, the result of `new` is often stored in a **smart pointer** (`std::unique_ptr` / `std::shared_ptr`). The pointers guarantee that the delete expression is executed
- The `new` _expression_ cannot be overloaded, but you can overload the _function_ `operator new` and `operator new[]` (as well as `operator free` and `operator free[]`)
    - C++ first invokes `operator new` to request raw bytes, then triggers the constructor inside the allocated memory block
    - You can implement custom memory allocation at _class specific_ scope_ (only affects a single class and its derivatives), or _global_ scope (replaces allocation logic for the _entire_ application)
    - Whenever you overload `operator new` in a class, always pair it with a matching `operator delete`
    - Overloading at the global namespace affects how _every_ default `new` allocation acts. This is common for building custom diagnostic loggers, or tracking application-wide leaks
    - You can append _custom arguments_ to the allocation function i.e. `void* operator new(std::size_t size, (params...))`. Note there must also be a matching delete with the same parameters. This follows the same mechanism as _placement new_
    ```cpp
    class A {
        static void* operator new(std::size_t, int i) {...}
        static void operator delete(void* ptr, int i) {...} 
        static void operator delete(void* ptr) {...}
    };
    A* a = new (10) A();
    ```
    - The matching `operator delete` with placement arguments is only called if `operator new` with those arguments successfully allocated memory **and** the constructor of `A` throws an exception. Otherwise, only the normal `operator delete` is called.
    - Conceptually, the compiler generates something like 
    ```
    void* mem = A::operator new(sizeof(A), 10);
    try {
        new (mem) A;
    } catch (...) {
        A::operator delete(mem, 10);
        throw;
    }
    ```
    - The extra placement argument is only used during allocation, and potentially during cleanup if construction fails. 



## `malloc/free` vs `new/delete`
- `malloc` only allocates memory; it does not initialize or construct the objects. You have to manually construct and initialize the objects 
    - You can use `memset` or `calloc` to zero initialize the allocated memory
    - In C++, you can use placement new 
    - Or you can use `std::make_unique` to safely allocate heap memory and wrap it in a single-owner smart pointer
- `new` allocates memory and calls the provided constructor 

`new` and `delete`
- you CANNOT use `delete` on `malloc`'d memory
- you also cannot free memory allocated using `new`
```cpp
int main() {
    int* i = (int*)malloc(sizeof(int));
    delete i; // UB
}
```
- `malloc / free` come from the C standard library. They allocate raw memory, tracked by the C runtime memory allocator
- `new / delete` are C++ operators. They not only allocate memory (usually also via the heap allocator under the hood), but they also: 
	- Call constructors (`new`), 
	- Call destructors (`delete`)
	- Maintain C++-specific allocation metadata 
- Mixing them breaks expectations 
	- `delete` expects metadata that `malloc` never set up (and calls the destructor on memory that never had a live object)
	- `free` won’t call destructors on objects allocated with `new`

## `std::unique_ptr`

- `std::make_unique` (C++14) is preferred over manually allocating memory using `new` and passing the pointer into a `unique_ptr` constructor 
    - It removes the need to explicitly write `new`, and prevents memory leaks if an exception occurs during the evaluation of function arguments 
    ```cpp
    auto a = std::make_unique<A>(x, y); 
    auto arr = std::make_unique<int[]>(5);
    ```
    - The limitation is that you cannot specify a custom deleter (like closing a file handling). You have to construct the `std::unique_ptr` directly 


`std::shared_ptr`
-  reference count is thread safe, but object access is not (does not synchronize read/writes to the object, only keeps the object alive using shared ownership)
- Access to the same `shared_ptr` object from multiple threads is **safe only if the access is read-only**
- the control block (which holds the reference count and deleter) is thread-safe with respect to incrementing and decrementing
- actual object managed by the shared pointer is not protected


### `sizeof` unique_ptr
```cpp
int main() {
    std::cout << sizeof(std::unique_ptr<int>);
}
```
- A `unique_ptr` is a RAII wrapper over a raw pointer. It adds no overhead to a raw pointer. Hence, it is the same size of a raw pointer, which is 8 bytes on 64-bit architecture.
- `shared_ptr` on the other hand, uses 16 bytes, one for the stored pointer `T* ptr`, one pointing to the control block


### `std::enable_shared_from_this<T>`

- Inherit from this class i.e. `class A : public enable_shared_from_this<A>` to enable returning a shared pointer to the current object using a member method using `shared_from_this()`
    - The naive method to return `std::make_shared<A>(this)` returns a _new_ shared pointer with a separate control block pointing to the same object. This can lead to double-free and use-after-free.
    - Under the hood, `enable_shared_from_this` has a `weak_ptr` data member pointing to itself. This prevents creating strong reference cycles 

## `std::allocator` 

- The purpose of an allocator is to separate the allocation of memory from calling the constructor for objects 
- For example, in `std::vector<int> v; v.resize(5);`, you don't want to construct the objects immediately, only allocate sufficient memory for the objects
    - Similarly, with `v.clear()`, you don't want to deallocate memory right away, only call the destructors 
    - As compared to `new T{}`, where the allocation and construction are done together and you have no control over it
- `std::allocator` is the default allocator for the standard library containers
- Member functions 
    - `allocate`
    - `allocate_at_least` 
    - `deallocate` 
    - `construct` 
    - `destroy`
    - `address`
    - `max_size`
- Helper template `std::allocator_traits<Alloc>`
    - Has static member functions `allocate(a, ...)`, `deallocate` etc. which just wraps around calling `Alloc::allocate(a, ...)` / `a.allocate(...)` etc.

### `std::default_delete`

`std::default_delete<T>` is the default destruction policy used by `std::unique_ptr` when no deleter is specified.

It has a single member function `void operator()(T* ptr) const` which calls `delete` on `ptr`.

It also has an array specialization to delete arrays.


## Small Object Optimization (SOO)
- Also known as Small Buffer Optimization (SBO)
	- It is a design pattern used to prevent expensive heap allocations for minor items
- SOO is when a class contains a fixed size internal buffer for small objects and a pointer for larger, heap-allocated objects.
	- It allocates a fixed-size internal buffer directly on the stack inside the object
	- If it is too large, the class falls back to a traditional heap allocation
- Where SOO is used
	- Small string optimization (SSO) skips heap allocation for strings shorter than 15-23 chars
	- `std::function`: Stores small, simple lambda functions natively to bypass dynamic allocation costs.
	- `std::any` uses internal byte arrays to avoid dynamic memory for small data types

## Stack, Heap
- Uninitialized global variables and uninitialized static variables are stored in `.bss` and are zeroed out before the program starts 
- Initialized global variables and initialized static variables are stored in `.data`
- Automatic (local) variables are stored on the stack

```cpp
static void foo() {
    int x = 1; // stored in stack
}

void bar() {
    static int y = 1; // .data
}

int main() {
    foo();
    bar();
}
```

```cpp
struct A 
{ 
    void foo() { } 
}; 

int main() { 
    A* x = new A(); // Ignore the cost of heap allocation here.
    A y;
    
    x->foo(); 
    y.foo(); 
}
```
- Without optimization, `x->foo()` is most likely slower due to extra level of pointer indirection (minor overhead)
- `x->foo()` requires reading the pointer x to get the address of the object and then calling the method on that address. This is two memory accesses. 
- `y.foo()` operates directly on the object, which is already in scope and typically resides on the stack (or in a register if optimized)
- With optimization, `x->foo()` and `y.foo()` can actually be optimized to the same set of assembly instructions. the overhead then comes from the fact that:
	- The stack-allocated object `y` is usually close to the current stack frame and often resides in the CPU cache. 
	- The heap-allocated object `x` might be in a different region of memory, possibly leading to more cache misses or less predictable locality
	- This effect can dominate in performance-critical or memory-intensive programs.

## `std::launder`
- Forces the compiler to read value from object again instead of reading it from cache 
- Usually used with `placement new` when a new object is created in place of old object
- Overwriting `const` field is UB, compiler expects the field to never be changed

## `std::addressof`
```cpp
struct Weird {
    int value;

    Weird* operator&() {
        std::cout << "Custom operator& called\n";
        return nullptr;
    }
};

int main() {
    Weird w;
} 
```
- `std::addressof(w)` Obtains the actual address of the object or function `arg`, even in presence of overloaded `operator&`
