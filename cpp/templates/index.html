Partial Specialization​

Functions​

  • You can't partially specialize a function (The C++ standard explicitly prohibits it), but you can overload it.
  • While class templates can be partially specialized, functions can only be fully specialized or overloaded.

Solution 1: Use Function Overloading (Recommended)​

Function templates can be overloaded. Instead of writing a partial specialization syntax, simply write another primary template that takes the more specific arguments.

// Generic base template
template <typename T, typename U>
void process(T a, U b) {
    // General logic
}

// "Partial specialization" via overloading for when U is a pointer
template <typename T, typename U>
void process(T a, U* b) {
    // Specific logic for pointers
}

Solution 2: Delegate to a Static Class Type​

If you must explicitly provide template parameters instead of relying on function arguments, delegate the function logic to a static helper class. Class templates do allow partial specialization.

// 1. Define a helper struct
template <typename T, typename U>
struct ProcessHelper {
    static void run(T a, U b) { /* General logic */ }
};

// 2. Partially specialize the struct
template <typename T, typename U>
struct ProcessHelper<T, U*> {
    static void run(T a, U* b) { /* Pointer logic */ }
};

// 3. Wrap it in a single clean function
template <typename T, typename U>
void process(T a, U b) {
    ProcessHelper<T, U>::run(a, b);
}

Solution 3: Use C++20 Concepts and Constraints​

In C++20, you can bypass specializations entirely by applying constraints (requires clauses) to guide the compiler

#include <concepts>

// General function used if constraints aren't met
template <typename T>
void handle(T val) {
    // General logic
}

// More constrained function (takes precedence when T is a pointer)
template <typename T>
void handle(T val) requires std::is_pointer_v<T> {
    // Pointer-specific logic
}

Template Argument Deduction​

template <typename T>
void foo(T&& arg) {
    T x;
    std::cout << x;
}

int main() {
    int i = 0;
    foo(i); // compile error
}
// T is deduced as int& , reference must be initialized on declaration so this doesn't compile
template <typename T>
requires std::is_integral_v<T>
void foo(T& p) {
    p = 1;
}

int main() {
    const int i = 0;
    foo(i); 
    // does not compile
} 
// i is deduced as const int, so any assignment to it is not allowed
template <typename ...Ts>
struct X {
    X(Ts ...args) : Var(0, args...) { }
    int Var;
};

int main() {
    X<> x;
    std::cout << x.Var; 
    // prints 0
}
// after substitution, Var(0, args...) is checked for the actual specialization used
// For X<>, that gives just Var(0), which is valid

auto type deduction​

int main()
{
    const auto t = std::make_tuple(1, 2., 3); // tuple<int,double,int>
    std::cout << std::get<int>(t); // compile error
}
  • std::get<T>(tuple) can only be used on a tuple which has exactly one T in it.
  • template< class T, class... Types > constexpr const T& get( const std::tuple<Types...>& t ) noexcept;
    •  Fails to compile if the tuple has more than one element of that type.

SFINAE​

Substitution Failure Is Not An Error

  • when template parameter substitution fails, the function is removed from the candidate set
  • sfinae only applies in the immediate context of the function, i.e. return type, template parameters
    • sfinae does not apply when there is a subtitution failure in the function body. those are treated as normal compile errors

std::enable_if

template <typename T>
std::enable_if_t<(sizeof(T) == 4)>
foo() {
    std::cout << "1";
}

int main() {
    foo<uint32_t>(); // prints 1
}
  • std::enable_if<bool b, typename T = void>
  • std::enable_if_t<b, T> is a helper for std::enable_if_t<b, T>::value
  • If T is not specified, it defaults to void
  • If the boolean condition evaluates to false, ::value is not defined thus causing SFINAE (the template function is just ignored)

Dependent Names​

  • Names that depend on template parameters
  • The compiler doesn't know what they refer to until the template is instantiated
  • Dependent names that are types must be prefixed with typename
template<typename T>
void foo() {
    typename T::value_type x;  // "value_type" is a dependent name
}

template<typename T>
class A {
    using B = typename T::x; // ok, T::x is a type and so is B

    using C = T::y; // here T::y is a static member, NOT a type

    typename T::x x_;
};
  • It can be used in function parameters.
template<typename T>
void foo(typename T::iterator it) { 
    // ...
}
  • .template disambiguates a dependent name in a template.
template <unsigned long N>
void printBitset(const std::bitset<N>& bs) {
    std::cout << bs.template to_string<char, std::char_traits<char>, std::allocator<char>>();
}
  • It tells the compiler that to_string is a template function, not a regular member function or type.
  • bs is a dependent type (depends on the template parameter N), so the compiler can't be sure whether to_string is a template or not without help.
  • By writing template, you're telling the compiler that to_string is indeed a template member function of std::bitset and you're supplying explicit template arguments.
  • Without the extra use of .template, the compiler does not know that the less-than token (<) that follows is not really less-than, but the beginning of a template argument list.
  • Note, this is only a problem if the method parameter (bs) depends on the template parameter (N).

Concepts​

Concepts lets you enforce constraints on template type parameters at compile time. A concept is just a compile-time boolean predicate. There are three main ways concepts / requires can be used.

// using concepts
template<typename T>
concept Integral = std::is_integral_v<T>;

template<Integral T>
void f(T x);

// using requires
template<typename T>
requires Integral<T>
void f(T x);

Predicates can be joined with logical operators.

template<typename T>
concept Arithmetic =
    std::is_integral_v<T> ||
    std::is_floating_point_v<T>;

template<Arithmetic T>
T square(T x)
{
    return x * x;
}

square(5);
square(3.14);
// square("abc); // invalid

template<typename T>
requires Integral<T> && sizeof(T) >= 4
void f(T);

Requires expressions checks if a set of expressions compiles. You can also check the return type of expressions.

// syntax: requires((optional) param-list) { requirement-sequence }
template<typename T>
concept Addable = 
requires(T a, T b) 
{
    a + b; // the statement "a+b;" must be able to compile
};

template<typename T>
concept EqualityComparable =
requires(T a, T b)
{
    { a == b } -> std::same_as<bool>; // "a == b" must return bool
};
template<typename T>
concept Incrementable =
requires(T x)
{
    { ++x } -> std::same_as<T&>;
};

// Multiple requirements
template<typename T>
concept VectorLike =
requires(T x)
{
    x.size();
    x.begin();
    x.end();
};

Concepts can be nested and built on each other.

template<typename T>
concept Addable =
requires(T a, T b)
{
    a + b;
};

template<typename T>
concept AddableAndComparable =
    Addable<T> &&
    requires(T a, T b)
{
    a == b;
};

You can also require nested types:

template<typename T>
concept HasValueType =
requires
{
    typename T::value_type;
};
HasValueType<std::vector<int>>   // true
HasValueType<int>                // false

The standard library defines a few concepts, which you can use out of the box.

std::integral
std::floating_point
std::same_as
std::derived_from
std::convertible_to
std::copyable
std::movable
std::default_initializable
std::constructible_from
std::assignable_from
std::invocable
std::predicate
std::regular

template<std::integral T>
void f(T);

void f(std::integral auto x);

Concepts also participate in overload resolution, with the more constraint function being preferred when both are viable:

template<typename T>
void print(T)
{
    std::cout << "generic\n";
}

template<std::integral T>
void print(T)
{
    std::cout << "integral\n";
}
print(5);      // integral
print(3.14);   // generic

Comparing with SFINAE, the concepts version is easier to read, gives clearer compiler diagnostics, and integrates directly into overload resolution.

// SFINAE
template<typename T,
         std::enable_if_t<std::is_integral_v<T>, int> = 0>
void foo(T);

// concepts
template<std::integral T>
void foo(T);

Tricky example​

template <typename T>
requires requires (std::is_arithmetic<T> x) { x + x; }
constexpr T add(const T a, const T b) {
    return a + b;
}
  • Compiles and is syntactically well formed, but it works for non-arithmetic types
  • Only x+x expression is required to be well formed
  • is_arithmetic<T> itself has operator bool() inherited from std::integral_constant, so the expression x+x is well formed
  • Hence here it does not matter whether T is arithmetic or not i.e. std::is_arithmetic<T>::value is false
  • This would work on strings e.g. add("a", "b") since strings support concatenation
  • The correct way would be requires std::is_arithmetic_v<T>, or requires requires(T t) { requires std::is_arithmetic_v<T>; }

Trailing Return types​

In C++, a trailing return type allows you to specify a function's return type after its parameter list. It requires using the auto keyword at the beginning as a placeholder.

Syntax Comparison:

  • Traditional Syntax: int add(int a, int b);
  • Trailing Syntax: auto add(int a, int b) -> int;

The primary reason this was introduced in C++11 is that the compiler cannot use function parameters before they are declared.

// This will NOT compile in C++11 (a and b are not yet known)
decltype(a + b) add(T1 a, T2 b); 

// This compiles perfectly
template <typename T1, typename T2>
auto add(T1 a, T2 b) -> decltype(a + b) {
    return a + b;
}

It makes pointers to functions or arrays much easier to read and format

// Traditional (unreadable)
int (*get_function(int space))(double);

// Trailing (clear hierarchy)
auto get_function(int space) -> int(*)(double);

Starting in C++14, you can often omit the trailing part completely. The compiler can deduce the return type directly from the return statement

// Valid since C++14
auto add(int a, int b) { 
    return a + b; 
}

Curiously Recurring Template Pattern (CRTP)​

  • compile time / static polymorphism

Template Definition​

// MyContainer.cpp
#include "MyContainer.hpp"

template <typename T>
MyContainer<T>::MyContainer(T val) : data(val) {}

// Tell the compiler to bake the code for these types explicitly:
template class MyContainer<int>;
template class MyContainer<double>;
  • Template declarations and definitions must reside entirely in header files because templates are not real functions or classes, but rather blueprints that the compiler uses to generate concrete code at compile time.
    • When a translation unit (.cpp file) uses a template, the compiler must see the full implementation to substitute the type parameters and generate the specialized object code.
    • If you put a template's definition in a separate .cpp file like a standard function, your code will compile but result in "undefined reference" linker errors whenever other files try to instantiate it
#ifndef EXAMPLE_HPP
#define EXAMPLE_HPP

template <typename T>
void print(const T& value);

#endif /// EXAMPLE_HPP

// example.cpp

#include <iostream>
#include "example.hpp"
template <typename T>
void print(const T& value)
{
    std::cout << value;
}

// main.cpp

#include "example.hpp"

int main()
{
    double cracked = 1.0;
    print(cracked);
}
  • This produces a linker error
    • The definition of the function template print(...) has not been instantiated
    • In order for a template to be instantiated, the compiler must know which definition should be instantiated and for what template arguments it should be instantiated.
    • When the compiler sees the call to print(), but has no definition in sight to instantiate this function for double, it just assumes that such a definition is provided elsewhere and creates a reference (for the linker to resolve) to that definition.
    • When the compiler then processes the file example.cpp, it has no indication at that point that it must instantiate the template definition it contains for specific arguments.
    • The common solution is to include the definitions of a template in the header file that declares that template.
    • Alternatively, we can keep example.cpp and, at the bottom, declare the template that needs to be instantiated, such as template void print;
      • This is called explicit template instantiation.

Templates with Packs​

Template sum:

template <typename ...Args>
auto sum(Args... args) {
    return (args + ... + 0);
}

int main() {
    auto x = sum(0.5, 2, 0.5, 2);
    auto y = sum(2, 0.5, 2, 0.5);
    std::cout << x << y; // prints 55
}
template <typename T, typename... U>
constexpr bool areSameType(T, U...)
{
    return (std::is_same_v<T, U> && ...);
}

int main() {
    std::cout << areSameType("upgrade", "to get", "cracked", "");
    // prints 1
}
  • The result yields true because all passed arguments are deduced to be char const* (the argument types decay because the call arguments are passed by value).

Practice Questions​

template <typename Type>
struct X {
    void bar() { std::cout << Type::identify() << std::endl; }
    static std::string_view identify() { return "X"; }
};

template <typename Type>
struct Y : Type {
    void bar() { std::cout << Type::identify() << std::endl; }
    static std::string_view identify() { return "Y"; }
};

class Z {
protected:
    void bar() { std::cout << identify() << std::endl; }
    static std::string_view identify() { return "Z"; }
};

int main() {
    Y<X<Y<Z>>>{}.bar(); // prints X
    Y<Z>{}.bar();       // Z
}
