Exceptions

Exception Handling​

Exception handling provides a way of transferring control and information from a point in the execution of a thread to an exception handler associated with a point previously passed by the execution.

A handler will be invoked only by throwing an exception in code executed in the handler's try block or in functions called from the handler's try block.

Throwing Exceptions​

  • An exception can be thrown from one of the following contexts
    • throw-expressions
    • allocation functions
    • dynamic_cast
    • typeid
    • new-expressions i.e. using new
    • standard library functions
  • Throwing an exception transfers control to a handler.
    • Control is transferred to the nearest handler with a matching type. "nearest" meaning the compound statement or ctor-initializer following the try keyword that was most recently entered and not yet exited
    • Throwing an exception initializes an object with dynamic storage duration, called the exception object.
      • If the type of object thrown is an incomplete type, an abstract class type, or a pointer to an incomplete type (other than cv void), the program is ill-formed.
    • If the handler exits by rethrowing the exception object, control is passed to another handler for the same exception object
    • The potential points for destruction for the exception object are
      • when an active handler for the exception exits by any means other than rethrowing, immediately after the destruction of the object (if any) declared in the exception-declaration (i.e. the catch (...) clause) in the handler
      • when an object of type std​::​exception_ptr that refers to the exception object is destroyed, before the destructor of std​::​exception_ptr returns
  • The implementation may then deallocate memory for the exception object. Any such deallocation is done in an unspecified way.
  • An exception is considered uncaught after completing the initialization of the exception object until completing the activation of a handler for the exception.
    • As a consequence, an exception is considered uncaught during any stack unwinding resulting from it being thrown.
  • If an exception object is rethrown, it is considered uncaught from the point of rethrow until the rethrown exception is caught.
  • An exception is considered caught when a handler for that exception becomes active.
  • If the exception handling mechanism handling an uncaught exception directly invokes a function that exits via an exception, the function std​::​terminate is invoked.
    • If a destructor directly invoked by stack unwinding exits via an exception, std​::​terminate is invoked

Stack Unwinding​

As control passes from the point where an exception is thrown to a handler, objects are destroyed by stack unwinding.

Each object with automatic storage duration is destroyed if it has been constructed, but not yet destroyed, since the try block was entered.

If an exception is thrown during the destruction of temporaries or local variables for a return statement, the destructor for the returned object (if any) is also invoked. The objects are destroyed in the reverse order of the completion of their construction.

struct A {
    A(char c) : c_(c) {}
    ~A() { std::cout << c_; }
    char c_;
};

struct Y { ~Y() noexcept(false) { throw 0; } };

A f() {
  try {
    A a('a');
    Y y;
    A b('b');
    return { 'c' };      // #1
  } catch (...) {
  }
  return { 'd' };        // #2
}

int main() {
    f(); // prints bcad
}

Exception Safety​

After an exception is thrown, there are four different levels of guarantees regarding the state of the program. They are strict supersets of each other.

  1. Nothrow (or nofail) exception guarantee (strongest): the function never throws exceptions
    • Nothrow is expected of destructors and other functions that may be called during stack unwinding
    • Destructors are noexcept by default (since C++11)
    • Nofail (i.e. the function always succeeds) is expected of swaps, move constructors, and other functions that provide strong exception guarantee
  2. Strong exception guarantee: If the function throws an exception, the state of the program is rolled back to the state just before the function call (e.g. std::vector::push_back)
  3. Basic exception guarantee: If the function throws an exception, the program is in a valid state. No resources are leaked, and all objects' invariants are intact
  4. No exception guarantee: If the function throws an exception, the program may not be in a valid state: resource leaks, memory corruption, or other invariant-destroying errors may have occurred
