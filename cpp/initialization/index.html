Initialization

Initialization provides a variable its initial value at the time of construction.

Types of Initialization​

There are a few types of initialization:

  • default initialization (no initializer)
    • T t;
    • new T
  • value initialization (empty constructor)
    • T()
    • T t{}
    • T{}
    • new T()
    • new T{}
    • Class::Class(...) : member() {...} (initializer list)
    • Class::Class(...) : member{} {...} (initializer list)
    • T t(); does not initialize a class (because of most vexing parse). The way to do direct initialization before C++11 is T t = T() to value-initialize a temporary and copy-initialize the object, where the copy is optimized away most of the time due to URVO
  • copy initialization (initialize an object from another object)
    • T t1 = t2;
    • T t1 = { t2 };
    • f(t) (passing argument by value)
    • return t (returning from function by value)
    • throw t; (throwing by value)
    • catch (T t2) (catching by value)
    • T arr[n] = { other-seq } as part of aggregate initialization
  • direct initialization (explicit set of arguments)
    • T t(arg);
    • T t(arg1, arg2, ...);
    • T t { arg };
    • T(t2);
    • T(arg1, arg2, ...)
    • static_cast<T>(t2)
    • new T(args, ...)
    • Class::Class() : member (args, ...) {...} (initializer list)
    • [arg]() {...} (capture by copy in lambda)
  • list initialization (initialize from brace-enclosed initializer list)
    • There is direct-list and copy-list initialization
    int main()
    {
    auto x = {1, 2, 3}; // std::initializer_list<int>
    auto y{1, 2, 3};    // compile error

    auto i(3);       // i is an int with value 3
    auto i{3};       // i is a std::initializer_list<int>
    }
    • x is std::initializer_list<int>, y is compilation error
    • auto y{1, 2, 3} with multiple values is a compilation error in C++17 onwards. Direct list initialization with auto requires exactly one element. For example, auto y{ 1 } is valid (deduces initializer_list)
    • https://stackoverflow.com/questions/25612262/why-does-auto-x3-deduce-an-initializer-list
  • aggregate initialization (also initialize from an initializer list)
    • It is a form of list initialization
  • reference initialization
  • non-local static and dynamic initialization

Reference Initialization​

  • References must be assigned when declared
  • They cannot be reassigned
  • The address of a reference is exactly the same as address of object it references
    • There is no such thing as pointer to a reference to an object
int main()
{
    const int a = 1;
    int& b = a; // does not compile, it drops const
    b = 2;
    std::cout << a;
}
int x;
&x; // returns a virtual address
  • Ampersand returns the address of x as it exists in the process. The process works with its own abstraction of physical memory, that being virtual memory.
struct C {
    int& a;
};

int main() {
    int y = 1;
    int z = 2;

    C c{y};
    c.a = z;

    std::cout << y << z << c.a; // prints 222
}

Summary Cheat Sheet​

MethodSyntax ExampleBest Used For...

Valueint x{};Safely resetting a variable to 0 or its default state.
Directint x(5);Calling specific multi-argument constructors. Be careful with the most vexing parse.

Nested initialization​

int x{42};

int main() {
    int x{x};
    std::cout << x;
    // prints junk
}
  • Each identifier 'x' in this problem exist in different scopes.
  • The printed value is not 42 because the global x is shadowed by the local x in main.
  • When we enter the curly braces to initialize x, it is already declared but still uninitialized.
  • The nested scope x inside of the initialization braces then looks outwards to the local scope x, which holds a garbage value and assigns it as such.
  • This initialization is functionally identical to: int x; x = x;

Copy Elision​

The compiler can optimize away constructor calls when initializing an object, so as to avoid creating unnecessary extra copies. The elision of object creation is known as copy elision. Certain conditions must be met first.

There is one main rule/use case where copy elision applies, though there are certain other niche cases where copy elision applies as well.

Named RVO​

In a return statement in a function with a class return type, when the operand is the name of a non-volatile object obj with automatic storage duration (other than a function parameter or a handler parameter), the copy-initialization of the result object can be omitted by constructing obj directly into the function call’s result object. This variant of copy elision is known as named return value optimization (NRVO).


Basically, in functions that return a class/struct object, and the object returned is a (non-static) local variable with a name (having automatic storage duration), the object is directly constructed in the target site. For example,

struct A {
    A() { 
        cout << "ctor " << this << '\n'; // prints address
    }
    A(const A& o) { 
        cout << "copy, this: " << this << ", other: " << &o << '\n'; 
    }
    A(A&& o) { 
        cout << "move, this: " << this << ", other: " << &o << '\n'; 
    }
    ~A() {
        cout << "dtor " << this << '\n';
    }
};

A f() {
    A o;
    return o;
}

int main() {
    A o1 = f(); // copy elision here
}

The function f returns a named object o. When o1 is created in the main function, the object is directly created at the call site (at the address for o1). Instead of calling the default constructor to create the local object o, returning it and calling the copy constructor for o1 (thus calling two constructors and having two objects in total), the object is directly constructed at o1 and only a single default constructor is called.

Running the program, you can expect to see an output like:

ctor 0x7ffcd3144d2f
dtor 0x7ffcd3144d2f

We can modify the function f to gain a better understanding. If we modify f as such:

A f() {
    A o;
    cout << "In f()\n";
    return o;
}

We will see the following output:

ctor 0x7ffcd3144d2f
In f()
dtor 0x7ffcd3144d2f

f still executes its statements normally line by line, but the object is constructed at the address of o1 only once using the default constructor. No copy constructor is invoked at all.

Unnamed RVO​

The other common case of copy elision is unnamed RVO.

When a class object target is copy-initialized with a temporary class object obj that has not been bound to a reference, the copy-initialization can be omitted by constructing obj directly into target. This variant of copy elision is known as unnamed return value optimization (URVO). Since C++17, URVO is mandatory and no longer considered a form of copy elision.

This form is also known as guaranteed copy elision (since C++17). Actually, since nothing is being elided, the standard does not formally consider it as copy elision.

Unnamed RVO applies when copy-initializing any class/struct using a temporary object (a prvalue) in general. The temporary value is not materialized until it is needed, and is constructed directly into the storage of its final destination. In the following example, all initializations only call the default constructor once, and no copy constructor is called.

A o2 = A();
A o3 { A() };
A o4 = { A() };

As no copy/move is performed, the type does not actually need to have an accessible move/copy constructor. We could declare the copy/move constructors as private and the following example would still work with unnamed RVO:

struct A {
public:
    A() { 
        cout << "ctor " << this << '\n'; // prints address
    }
    ~A() {
        cout << "dtor " << this << '\n';
    }
private:
    A(const A& o) { 
        cout << "copy, this: " << this << ", other: " << &o << '\n'; 
    }
    A(A&& o) { 
        cout << "move, this: " << this << ", other: " << &o << '\n'; 
    }
};

void g(A a) {} // unnamed RVO also applies to function parameters

A h() {
    return A();
}

int main() {
    g(A(h()));
}

The output of the program above is a single call to the constructor and destructor.

ctor 0x7ffe5a4a948f
dtor 0x7ffe5a4a948f

This also demonstrates how copy elision can be combined to eliminate multiple copies. The only condition to take note of here is that the destructor must be accessible and non-deleted.

There is one more caveat: in order for guaranteed copy elision to apply, the type of the temporary object returned must be the same as the return type of the function. In the following example, URVO does not apply as the return type and the object type are not the same:

struct A {
    A() { 
        cout << "[A] ctor " << this << '\n'; // prints address
    }
    ~A() {
        cout << "[A] dtor " << this << '\n';
    }
    A(const A& o) { 
        cout << "[A] copy, this: " << this << ", other: " << &o << '\n'; 
    }
    A(A&& o) { 
        cout << "[A] move, this: " << this << ", other: " << &o << '\n'; 
    }
    int x = 1;
};

struct B : A {
    B() { 
        cout << "[B] ctor " << this << '\n'; 
    }
    ~B() {
        cout << "[B] dtor " << this << '\n';
    }
    B(const A& o) { 
        cout << "[B] copy, this: " << this << ", other: " << &o << '\n'; 
    }
    B(A&& o) { 
        cout << "[B] move, this: " << this << ", other: " << &o << '\n'; 
    }
    int y = 2;
};

A h() {
    return B(); // no copy elision: a temporary B is created, then A's move (preferred) 
                // or copy ctor is called
                // this is object slicing - only x survives, y is lost;
}

int main() {
    h(); 
}

The output is as follows:

[A] ctor 0x7ffd77ed952f
[B] ctor 0x7ffd77ed952f
[A] move, this: 0x7ffd77ed955f, other: 0x7ffd77ed952f
[B] dtor 0x7ffd77ed952f
[A] dtor 0x7ffd77ed952f
[A] dtor 0x7ffd77ed955f

From the output, we can see that A's constructor is called first, followed by B (as per normal constructor hierarchy). Then since the return type B() is not the same as the function's return type A, there is no guaranteed copy elision. A's move constructor is called to create an object of A (at 0x7ffd77ed955f) to be returned. It moves from the A subobject (at 0x7ffd77ed952f) inside the B object. The moved-from object is then destroyed, with the destructors being called in reverse. Finally, the return value from h() is discarded, so the returned A object's destructor is called.

Special cases​

In a throw expression, when the operand is the name of a non-volatile object obj with automatic storage duration (other than a function parameter or a handler parameter) that belongs to a scope that does not contain the innermost enclosing try block (if exists), the copy-initialization of the exception object can be omitted by constructing obj directly into the exception object.

A a;
try {
    throw a;
} catch (const A& o) { // copy elision here
}

Lastly, in constant expressions and constant initialization, copy elision is never performed.

Other notes​

Copy elision only applies for initialization, i.e. object creation (giving an initial value at the time of construction). It does not apply for assignment operators.

A a;
a = A(); // default ctor, move assignment, then dtor is called

Copy elision is one of two allowed forms of optimization, alongside allocation elision and extension (using new) that can change observable side effects since C++14. That is, even if constructors/destructors have side effects, the compiler is allowed to change the observed behaviour. Prior to C++14, copy elision was the only allowed form of optimization. Thus, programs should not rely on the side effects of copy/move constructors and destructors.

In a return or throw expression, if the compiler cannot perform copy elision but the conditions for copy elision are met, or would be met except that the source is a function parameter, the compiler will attempt to use the move constructor even if the source operand is an lvalue (until C++23) / the source operand will be treated as an rvalue (since C++23).

Disabling NRVO​

Copy elision can be disabled using the flag -fno-elide-constructors. This flag forces the compiler to call copy and move constructors in places where they would normally be optimized away. This may be useful for debugging lifecycles and tracking the exact creation, copying, and destruction of objects.

With C++17, this flag does not disable all elision. URVO is guaranteed by the compiler so it cannot be disabled. This means returning an unnamed temporary, initializing an object from a temporary etc. will still only result in a single constructor call. The flag can only disable NRVO where you return a named variable.

class A {
public:
    A() { std::cout << "1"; }
    A(const A& copy) { std::cout << "2"; }
    ~A() { std::cout << "3"; }
};

A createA() {
    A temp {};
    return temp;
}

int main() {
    A a { createA() }; // prints 123233

    // temp is created, calls default constructor - 1
    // temp is copied into the call site createA(), calling copy constructor - 2
    // temp is destroyed, calling dtor - 3
    // copy constructor is invoked to initialize a - 2
    // the copy is destroyed - 3
    // lastly, a is destroyed - 3
}
